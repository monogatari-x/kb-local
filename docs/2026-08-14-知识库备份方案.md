# 知识库备份方案

- 日期:2026-08-14
- 类型:运维/容灾

## 背景

各项目下的 `docs/`、`doc/` 目录被各仓库 gitignore,不进版本控制,本机硬盘是唯一存放点。kb-local 虽对其做了索引(切片 + 嵌入),但切片是加工副本,原始文档一旦随硬盘损坏丢失即无法恢复。因此将**原始文档 + SQLite 索引**定期同步到测试服务器做容灾备份。

## 备份什么(数据层次)

| 数据 | 内容 | 是否备份 | 可重建性 |
|---|---|---|---|
| 各项目 `docs/`、`doc/` 原始文档 | 知识本体(唯一副本) | ✅ 全量镜像 | 不可重建,最高优先级 |
| `~/.kb/kb_meta.db` | 元数据 + 切片文本 + 嵌入缓存(51MB) | ✅ 快照 | 可从 docs 重建,缓存加速恢复 |
| Qdrant 向量库 | 检索向量 | ❌ | `kb jobs run --type full_scan` 可重建 |
| BGE-M3 模型 | 权重(~5GB) | ❌ | 可重新下载 |

## 命令

```bash
# 只预览计划,不传输
uv run python scripts/backup.py --dry-run
# 正常增量备份
uv run python scripts/backup.py
# 增量 + 删除远端已不存在的文件(默认只增不删)
uv run python scripts/backup.py --prune-stale
```

连接参数(均有 CLI 默认值,可用选项覆盖):`--server 192.168.0.10 --user caopingtao --key ~/.ssh/id_rsa_2048 --remote /home/caopingtao/RAG/bak`。

## 机制

- **文件选择**:复用 `kb jobs run` 的 include/exclude 规则(`kb_core/utils/paths.py`),保证"索引了什么就备份什么"。
- **增量**:本地维护 `~/.kb/backup_manifest.json`(sha256 清单),只推送变更/新增文件。`kb_meta.db` 快照每次重新生成、每次重推(51MB,内网 1-2s)。
- **一致性**:SQLite 用官方 `.backup` API 快照(WAL 模式下直接拷文件可能损坏)。
- **远端只增不删**:避免文档临时移走时远端副本被误删;确认要同步删除再传 `--prune-stale`。
- **平台**:优先 Windows 原生 OpenSSH(`System32\OpenSSH`) + `D:/` 路径,兼容 Git Bash 与定时任务 cmd 环境。

## 远端结构

```
/home/caopingtao/RAG/bak/
├── kb_meta.db             # 最新 SQLite 快照
├── backup_meta.json       # 备份元信息(时间/文件数/字节数)
└── Glow/Projects/...      # docs/doc 镜像,保留本机目录层次
```

## 定时任务

- 任务名:`kb-local-backup`,每天 17:00(`schtasks` 注册)。
- 入口:`scripts/backup_scheduled.bat`(cd 到项目根 + `uv run python scripts/backup.py`),日志追加到 `%USERPROFILE%\.kb\backup.log`。
- 仅用户登录时运行(默认交互式);如需登出也跑,需提供密码并改用 `/RU` + 存储凭据。

## 恢复流程

```bash
# 新机器装好 kb-local + Qdrant 后:
scp -r caopingtao@192.168.0.10:/home/caopingtao/RAG/bak/ ~/restore/
# 1) kb_meta.db 放回 ~/.kb/
# 2) Glow/Projects 镜像按原路径归位到 D:/Glow/Projects
uv run kb jobs run --type full_scan   # 重建 Qdrant 向量,嵌入缓存命中,秒级
```
