# 知识库索引修复与 watch 收紧(2026-09-14)

## 背景

用户怀疑 `D:\Glow\Projects\` 下大量 md 文档未进入本地知识库。核实属实,并顺藤发现更深的 loader 缺陷。本文记录排查过程、三项修复与验证结果。

## 问题一:93 个 md 未索引(索引任务连续失败)

### 现象

- glow-projects watch(`*/docs/*`、`*/doc/*`)磁盘 192 个 md,库内仅 99
- yaf/docs watch 磁盘 135 个 md,库内仅 57
- 缺失文件 mtime 全部集中在 2026-08-13 之后——最后一次成功索引停在 08-13/08-14

### 根因(jobs 表 error_log)

1. **SOCKS 代理环境变量未清**:shell 有 `ALL_PROXY=socks5h://192.168.1.10:1988`,`_build_pipeline` 阶段 qdrant_client 因 socks 依赖缺失 import 失败,任务 0 文件处理即崩(09-14 当天两次 incremental 均如此)
2. **内存不足 + 重复并发**:两个索引器并发(各加载 BGE-M3 ~1.4GB)vs 剩余 887MB,被 kill
3. **09-03 full_scan 中断成 stale** 悬挂至 09-14

### 修复动作

1. `taskkill /PID <卡死索引器> /T /F`(残留进程占 1.6GB)
2. 清代理后串行跑增量:`env -u ALL_PROXY -u all_proxy -u HTTP_PROXY -u http_proxy -u HTTPS_PROXY -u https_proxy uv run kb jobs run --type incremental`
3. 结果:1397/1476 成功(79 个 FAIL 全为 png/无扩展名等无 loader 文件,预期内),md 192/192 全部入库

## 问题三:markdown 正文从未入库(loader 核心缺陷)

### 现象与证据

- 全库 9789 个 chunk 中**没有任何正文段落类切片**(仅 heading/code/mixed)
- 纯文本 md(无标题无代码块)切出 0 chunk,完全搜不到
- 带标题文档只有标题文字与代码块入库,正文段落全部丢失

### 根因

`kb_core/loaders/markdown_loader.py` 的 `_extract_blocks`:`paragraph_open` 分支只更新 `line_offset`(死变量)从不创建 Block;`_fill_paragraph_text()` 为空实现(`return blocks`,未完成的 TODO)。而 `MarkdownChunker` 只对 `kind="paragraph"` 的 block 做正文切片 → 正文永远为空。

### 修复(TDD)

- RED:tests/unit/test_markdown_loader.py 加 `test_load_extracts_paragraph_blocks`、`test_plain_text_note_yields_paragraph_block`;test_markdown_chunker.py 加 `test_end_to_end_plain_note_produces_chunks`、`test_end_to_end_body_text_indexed`
- GREEN:`paragraph_open` 分支用 `lines[start_line-1:end_line]` 行切片创建 `Block(kind="paragraph")`;删除死变量与空壳方法
- 全部 130 个单测通过,ruff/format/mypy strict 通过

### 测试编写踩坑

`Path.write_text("A\r\nB\r\n")` 在 Windows 默认 newline=None 会把 `\n` 翻译为 `\r\n`,字符串自带的 `\r\n` 变 `\r\r\n`;孤立 `\r` 使 `splitlines()` 与 markdown-it 的行号语义错位。测试写含 `\r\n` 的内容必须 `newline=""`。(真实文件经 `read_text` universal newlines 归一化,无此问题。)

## 问题四:parser_version 未参与跳过判断(loader 升级无法触发重索引)

### 现象

loader 修复后重跑 incremental,chunks 里依然没有 paragraph——`indexing.py:59` 的跳过条件只比对文件 sha256 + status,文件没变就直接 return。`parser_version` 字段一直写入 `"0.1.0"` 硬编码,从未参与检测,parser 升级后旧文档永远不重切。

### 修复(TDD)

- `kb_core/pipelines/indexing.py`:新增模块级 `PARSER_VERSION = "0.2.0"` 常量;跳过条件加 `existing.parser_version == PARSER_VERSION`;文档写入用常量
- 单测 `tests/unit/test_indexing_pipeline_skip.py`(fake embedder/qdrant + 真 SQLite):①同版本未变文件跳过;②parser_version 过期强制重切、正文 chunk 恢复
- 以后升级 loader/chunker 逻辑时,只需 bump `PARSER_VERSION`,下次 incremental 全量重切

## 问题五:MCP server 连接频繁超时(启动慢于 30s 默认超时)

### 现象

多个 Claude Code 会话(不同项目目录)`kb-local` MCP 连接报
`connection timed out after 30000ms`,`/mcp` 重连也失败。日志目录:
`~/AppData/Local/claude-cli-nodejs/Cache/<项目>/mcp-logs-kb-local/*.jsonl`。

### 排查(证据链)

- `kb_mcp/` 相对 HEAD **无任何改动**——不是代码被改坏
- 成功会话日志:Qdrant 在 3 秒响应(200 OK),**26.1 秒**完成连接
- 失败会话日志:Qdrant 在 20 秒才响应,30.07 秒超时;stderr 停在 Qdrant 请求之后
- 实测各环耗时:`uv run` 启动 0.56s(直连 venv 0.34s,不值得优化)、`import torch`
  **12s**(随 CPU 争用 2~12s)、HF 元数据查询有代理 3s / **无代理 24s 挂死**、
  BGE-M3 加载 ~11s
- 失败历史可回溯到 **09-03**,一直间歇出现(同日既有成功也有失败),并非近期新增

### 根因

`kb_mcp/server.py` 的 `prewarm()` 在 `mcp.run()` **之前、主线程内同步**加载
BGE-M3(2.4GB)。启动总耗时 26~52s(受 CPU/磁盘争用放大),**横跨 Claude Code
的 30 秒 MCP 启动超时线**,故表现为"有时连得上、有时超时"。与 SOCKS 代理
只间接相关(代理只影响 HF 网络调用那 3~24s)。

注意:prewarm 的异常是被捕获的(仅告警不退出),所以 ImportError 之类的快速失败
**不会**导致连接超时;只有"慢"才会。

### 已应用的缓解(2026-09-14)

`~/.claude/settings.json` 的 `env`(已备份 `settings.json.bak-20260914`):

- `MCP_TIMEOUT=120000`——给足模型加载余量
- `HF_HUB_OFFLINE=1`——对 CLI 路径有用(MCP 本来就有,见下)

实测:索引任务占满 CPU 时握手仍需 52.5s,故 120s 余量是必要的。
**需重启 Claude Code 会话生效**(settings 的 env 在进程启动时注入)。

**更正**:`kb_mcp/__main__.py` 第 6 行本来就有
`os.environ.setdefault("HF_HUB_OFFLINE","1")`,所以 MCP server 一直是离线模式,
HF 网络从来不是它启动慢的原因。**真正的修复只有 `MCP_TIMEOUT`。**

### 根治:共享长驻 HTTP server(2026-09-15 实施)

`kb_mcp/server.py` 增加传输开关(向后兼容,不设变量时行为与原先完全一致):

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `KB_MCP_TRANSPORT` | `stdio` | `http` 或 `streamable-http` 则起 HTTP 服务 |
| `KB_MCP_PORT` | `8765` | 监听端口(非法值回退默认) |
| `KB_MCP_HOST` | `127.0.0.1` | 仅本机;HTTP 模式启用 `stateless_http` |

配套:`scripts/verify_mcp.py` 扩展为双传输验证
(`--transport http --url ... --query "..."`),httpx 客户端显式 `trust_env=False`
以绕开 shell 的 SOCKS 代理。

**实测结果**:

| 项目 | stdio(旧) | HTTP(新) |
|---|---|---|
| 握手耗时 | 26~52s(卡 30s 超时线) | **0.05s** |
| 8 路并发检索 | 不适用(单客户端) | **8/8 成功**,总墙钟 3.1s,无锁错误 |
| 模型内存 | 每会话各 1.9GB | 常驻 **1 份** |

服务端进程实测占 1951MB(比预估 1.4GB 高)。日志零异常、零 `database is locked`。

未验证项:写入并发(索引任务运行时发起检索)因索引已结束而未能覆盖;
`journal_mode` 仍是 `delete`(写阻塞读),见遗留。

### 部署与切换(2026-09-15)

- `~/.claude.json`(已备份 `claude.json.bak-20260915`)中 kb-local 由 stdio 改为
  `{"type":"http","url":"http://127.0.0.1:8765/mcp"}`;**必须移除而不是并存**,
  否则会话仍会 spawn stdio 副本、模型照旧加载两份
- 切换后 `claude mcp list`:`kb-local: http://127.0.0.1:8765/mcp (HTTP) - ✔ Connected`,
  总耗时 **2.7s**(对比 stdio 的 26~52s),且**未 spawn 新进程**
- **自启用启动文件夹而非任务计划**:`Register-ScheduledTask` 与 `schtasks` 均返回
  拒绝访问(需管理员,当前会话无法提权),故放
  `%APPDATA%\...\Startup\kb-local-mcp-http.lnk`。代价是没有任务计划的"失败自动重启",
  改在 `start_mcp_http.bat` 里用 5 秒自愈循环补齐
- **需重启 Claude Code 会话生效**(MCP 配置在会话启动时读取)

### 顺带修好:启动器硬编码了不存在的 C: 盘路径

排查自启时发现 `start_watcher.bat/.vbs`、`start_docker.bat/.vbs` 四个脚本里都写死
`C:\Glow\Projects\kb-local`,而项目**已迁到 D 盘**。这解释了任务
`kb-local-watcher` 形同虚设、以及 `watcher.log` 里
`watcher exited with code -1`——脚本 cd 到不存在的目录,后续命令自然失败。

修法照项目自己的正确样例 `backup_scheduled.bat`:

- 一律 `cd /d "%~dp0.."` 用**脚本自身位置**定位项目根(VBS 侧用
  `fso.GetParentFolderName(WScript.ScriptFullName)`),以后再搬盘也不会失效
- 顺带清 `ALL_PROXY` 等代理变量:`_build_pipeline` 在 SOCKS 代理下会
  ImportError(与问题一同源),watcher 也要建同一条管线
- `echo` 之后补 `exit /b %errorlevel%` 透传退出码,否则"失败自动重启"永不触发

**排查中的两个坑**:

1. **Write 工具写出的 .bat/.vbs 是 LF 换行**,而 Windows 批处理对 LF 敏感
   (带 `goto` 标签的脚本直接失效——表现为日志一行都没写)。必须转回 CRLF。
   注意 `grep -q $'\r'` 在 Git Bash 里判断换行**不可靠**,要用 Python 读字节复核。
2. Git Bash 会把 `schtasks /create` 的 `/create` 当路径转换成 `D:/Softwares/Git/create`,
   需加 `MSYS_NO_PATHCONV=1`。

**验证状态**:路径修复已用 `cd /d "%~dp0.."` 实测解析到
`D:\Glow\Projects\kb-local`;但**watcher 的完整启动(含模型加载)未复验**——
当时 MCP 服务已占一份模型,再起 watcher 会内存争抢,留待下次登录自然验证
(新脚本日志会打印 `dir=` 便于确认)。
