## 一、遗留项处理

### 1. SQLite 切 WAL + busy_timeout ✅

`kb_core/stores/sqlite_store.py` 连接时执行 `PRAGMA journal_mode = WAL` 与
`PRAGMA busy_timeout = 5000`。WAL 是库级持久属性,设置一次后所有连接生效;
busy_timeout 让锁竞争时等待而非立即报 `database is locked`。

新增 `tests/unit/test_sqlite_wal.py`(4 例):WAL 生效与持久性、busy_timeout
配置、EXCLUSIVE 写锁下读者不被阻塞、3 线程并发写 60 次全部成功。

生效方式:重启 MCP 服务(bat 自愈循环自动拉起)后确认
`PRAGMA journal_mode` → `wal`。

### 2. PARSER_VERSION 按 file_type 分版本 ✅

原全局单值改为 `PARSER_VERSIONS: dict[str, str]`(code/markdown/text 各自独立,
当前均为 "0.2.0" 以匹配库中现状,避免一次无谓重切)。跳过判断按文档的
chunker_key 查表。今后只升 markdown loader 时只 bump markdown 版本,
code/text 文档不再被连带重嵌入。

新增测试:code 文档在 markdown 版本被 bump 后不重切(embedder 调用数不变)。
chunker_key 计算提取为 `_chunker_key_for()` 并移到跳过判断之前。

### 3. MCP 启动前等待 Qdrant ✅

`start_mcp_http.bat` 仿 `start_docker.bat` 的 wait 模式:启动前 curl 探测
`127.0.0.1:6333`(最多 180s,超时则照常启动并记日志);自愈循环每次重启也
重走等待——进程挂掉的原因可能正是 Qdrant 掉了。
动机:prewarm 在 Qdrant 未就绪时失败,之后首次检索只能在 anyio 工作线程
加载模型,而 `server.py` 注释明确记录该路径有 GIL 死锁历史。

实测:重启服务时日志出现 `Qdrant is ready (waited 5s)`。

### 4. watcher 复验 ✅(过程曲折,结论:旧实例"活而僵死",重启后端到端打通)

## 二、Codex CLI 适配(结论:已打通,零代码改动)

### 调研结论

Codex CLI(v0.158)支持 MCP,`config.toml` 的 `[mcp_servers.<name>]` 同时支持
stdio 与 streamable HTTP(`url` 字段);管理命令 `codex mcp add/get/list/remove`。
关键是 **kb-local 的 HTTP 传输改造让适配变成了纯配置工作**——同一份常驻服务
同时服务 Claude Code 与 Codex,模型仍只有一份。

### 实施与验证(2026-09-28 实测)

1. 接入:`codex mcp add kb-local --url "http://127.0.0.1:8765/mcp"`
   (写入全局 `~/.codex/config.toml`)。`codex mcp list` 显示
   `kb-local http://127.0.0.1:8765/mcp enabled`。
2. 真实调用验证:`codex exec` 在 yaf 目录提问,模型调用 kb_search 返回
   `2026-08-03-专家评审回避规则功能归档.md:16-17 score=0.500`,
   与 Claude Code 侧结果一致。
3. **交互式(TUI)使用正常**;**headless(exec)场景需注意**:
   HTTP MCP 的工具调用默认要 approval,`approval: never` 时会被拦
   (`MCP tool call requires approval`),测试时用
   `--dangerably-bypass-approvals-and-sandbox` 通过。正式 headless 场景
   应按 Codex 文档配置 MCP 审批策略而非裸 bypass。

### 踩坑记录

- **`GET /mcp → 406 Not Acceptable` 是正常现象**:MCP streamable HTTP 规范上
  `/mcp` 只收 POST(带 `Accept: application/json, text/event-stream`)。
  Codex 连接前的 GET 探测与 OAuth 发现(`.well-known/*` → 404)都会在服务端
  日志留下"失败"痕迹,实际握手不受影响——不要被日志误导。
- **项目级 `.codex/config.toml` 的 mcp_servers 未被 `codex mcp list` 识别**
  (该命令只读全局)。本仓库根的 `.codex/config.toml` 保留作声明,实际生效
  的是全局配置。
- Codex Desktop 的 CLI 不在 PATH:
  `C:\Users\Lenovo\AppData\Local\OpenAI\Codex\bin\<hash>\codex.exe`。

### 其他机器部署清单(Codex 侧)

1. 保证 kb-local 的 HTTP 服务在该机运行(拉代码 + `kb watch add` +
   启动 `scripts/start_mcp_http.bat`,或访问中心化的 kb 服务改 URL 指向远端)
2. `codex mcp add kb-local --url http://<host>:8765/mcp`(注意 HOST 需允许
   远端访问时设 `KB_MCP_HOST=0.0.0.0`,并自行加认证——当前服务无鉴权,
   仅本机回环安全)
3. `codex mcp list` 确认 enabled;TUI 首次调用工具时批准一次
